## Required operator journey and acceptance

1. Operator copies unchanged ISO and the built minimal Ubuntu RAW host container to m-boot's filesystem. A GRUB/EFI menu entry selects the original ISO and passes its real filesystem location to the RAW Ubuntu host.
2. Existing GRUB (no core rebuild) loads the selected host kernel/initramfs from the container or a justified, revision-bound sidecar. The host kernel/initramfs finds the RAW root filesystem file again, rather than assuming GRUB's loopback persists after handoff.
3. Minimal Ubuntu host starts without interactive distro setup, identifies native CPU architecture (x86_64 or aarch64), chooses its matching QEMU system emulator, uses actual KVM only if supported and demonstrably enabled, otherwise compatible TCG where feasible. RAM/CPU/firmware/graphics are separately characterized.
4. Guest receives unchanged selected ISO via persistent read-only virtual CD; provide honest guest-side post-kernel and original-vendor recognition evidence rather than host-only flags or an EFI-only menu.
5. The **full physical-disk inventory** is visible to the VM, including boot/source media. Host source disk must stay safe while hosting RAW/ISO files, so guest can be exposed a read-only view; other physical disks begin read-only unless exclusive ownership and explicit write authorization are demonstrated. Enabling writes on a device mounted or otherwise active in host is prohibited. The operator still needs a controlled route to explicitly authorize writes for real installation/backup tasks. Do not quietly omit the boot/source disk or claim all-disks available if devices cannot be attached.
6. Full source and physical disk integrity checks, isolation/cleanup, bounded failure paths and an operator-usable GRUB menu entry require real tests. Firmware/serial/graphics and host-bare-metal device/permission limitations must be recorded.
7. No current acceptance of raw USB writes, unattended disk installation, physical disk overwrite, real host boot success, or production-ready menu entry without authenticated execution and tests. CI must use **disposable fixture disks only**.

## Current operator-approved design — native Ubuntu loop root (2026-11-05)

- **Corrected by the operator:** produce a **partitionless ext4 filesystem image** in the RAW file, not a GPT/whole-disk RAW. Use Ubuntu's existing `initramfs-tools` `loop=` mechanism rather than inventing GPT offsets, private loop-root hooks or a new filesystem mount implementation. The original Canonical Ubuntu Minimal QCOW2 **input may still contain GPT** for build/customization; only its ext4 root filesystem is extracted and published as the RAW output. The user explicitly confirmed this design.
- **Kernel and initramfs external to the RAW**, same version/build as the customized Ubuntu root filesystem: one AMD64 or ARM64 bundle under `/m/boot/host/<arch>/` contains `mboot-ubuntu-host.raw`, `vmlinuz`, `initrd.img`, `kernel-release.txt`, `release-SHA256SUMS`. The compressed `.raw.zst` is transportation only. Maintain integrity and build identity across all bundle members; GRUB loads `vmlinuz` and `initrd.img` directly from ext4 MBOOTDATA.
- GRUB passes `root=UUID=<MBOOTDATA ext4 UUID>`, `loop=<architecture-specific RAW filesystem pathname>`, `loopfstype=ext4`, `mboot.iso=<selected unchanged ISO pathname>` and suitable console flags. Ubuntu native `scripts/local` first mounts MBOOTDATA, then moves it to `/host`, loop-mounts the ext4 RAW image as the new root, and preserves `/host` across switch-root. The QEMU launcher finds the original ISO under `/host` without mounting MBOOTDATA a second time. **No custom GPT partition scanner, initramfs local-top, local-bottom or hook is used.**
- Verify the native loop capability against the actual Ubuntu `initramfs-tools-core` version **both** on the build runner and *inside the customized Ubuntu image*; do not infer availability solely from a manpage. A real Ubuntu 24.04 GitHub Actions runner was inspected in [42090302581](https://github.com/massimilianonardi-ai/rumiai-dev-PoCs/actions/runs/42090302581), source `c403c599cd25b291006f3e7ffd073c67e2abdcf2`, `initramfs-tools-core 0.142ubuntu25.8`, with `LOOP` and `mount -o move` present in the installed `/usr/share/initramfs-tools/scripts/local`. A real disposable unpartitioned ext4 filesystem image passed `blkid` and `e2fsck -fn` in that job. This is **source/script/fixture validation only**, not a successful Ubuntu host boot.
- Original upstream behavior cross-check: Ubuntu 24.04 manual https://manpages.ubuntu.com/manpages/noble/man7/initramfs-tools.7.html ; Ubuntu's `scripts/local` native implementation from the Ubuntu 0.130 source is visible at https://www.apt-browse.com/browse/ubuntu/bionic/main/all/initramfs-tools-core/0.130ubuntu3/file/usr/share/initramfs-tools/scripts/local ; historical Wubi GRUB `root=... loop=/ubuntu/disks/root.disk` usage at https://help.ubuntu.com/community/Grub2/Troubleshooting . Historical Wubi evidence is used solely for mechanism verification, not as product authority.
- PoC files currently owning this work: `rumiai-dev-PoCs/pocs/qemu-ubuntu-raw-host/{build.sh,grub-example.cfg,launch.py,mboot-qemu-host.service,smoke.py,README.md}` and `.github/workflows/m-boot-ubuntu-raw-host.yml`. Three redundant custom GPT boot hooks were deleted **forward-only**. The GRUB file remains an **experimental function, not wired to m-boot's menu**.
- This architectural correction does **not** claim RAW build success, nested UEFI/GRUB boot, a guest recognizing the selected ISO, KVM acceleration or real physical disk attachment. Keep previous QEMU optical fixture evidence and the current default **read-only** physical disk plan strictly within their tested scopes.
