# Advanced browser/Electron text editor

Status: Active — DOM-independent text engine correctness prioritized; compensated selection failures tested, permanent backend selection and Unicode editing semantics still experimental
Updated: 2026-10-11

## Goal

Design and eventually build an extremely fast, memory-efficient advanced JavaScript text editor capable of handling very large documents while retaining MadEdit-Mod-like intuitive 2D/non-linear editing semantics. Keep a powerful text-management core independent of a lightweight browser DOM UI and usable by optional Electron hosts.

The JavaScript compilation, module loading and distribution concern has **independent ownership** at `handoff/javascript-build-and-runtime-loading.md`. This handoff must not make bundler/loader decisions.

## Fixed task-local choices

- This editor is an independently useful product, not a test fixture for a bundler or an extension of the terminal `vsed`.
- MadEdit-Mod is the starting functional benchmark; its unusually intuitive multiline/Excel-column/CSV paste across many target lines is a defining requirement, beyond generic rectangular selection or multicursor parity. Exact outcomes for differing source/target shapes must be characterized rather than assumed.
- Extreme editing speed, low memory footprint, and responsiveness on very large documents are primary acceptance constraints, not later optimizations. Test realistically rather than promising size-independent latency for operations inherently touching huge ranges.
- Monaco, CodeMirror, Ace and comparable existing editor libraries are excluded as the new editor's engine: inspect their useful concepts/techniques, but do not select or embed them as the editor architecture. PoC 061 remains historical feasibility evidence only.
- Generalize multiple cursors/selections as a foundation for several 2D/non-linear editing modes, rather than implementing only one rectangular-selection special case.
- **User-fixed 2026-10-10, evolving ownership:** keep undo/redo, journal, persistence, and action interpretation external to the editing model. The latest user-proposed decomposition (2026-10-10) introduces a selection-free text-store interface, provisionally named `TextEditBase`, below a selection-owning layer `TextEditSelections`; a higher column-edit planner prepares targets/content rather than embedding mode flags in either lower level. All layers remain independent of browser DOM. The outer action/history wrapper remains responsible for one undo record per user action. Exact class hierarchy, method signatures and transactional internals are still candidate working design, not promoted product API.
- **User-fixed 2026-10-10, selections and input scope (clarified by new layering):** the **selection-editing layer** owns all oriented selections and cursors as zero-length selections; the *base text-storage interface* owns **no selections**. The outer action/history wrapper may interpret input and prepare selections but does not own canonical selection state. Forward/undo/redo restore selection-layer state. Multiple physical keyboards feed one unified ordered logical input stream. Independent keyboards and collaborative/concurrent editing synchronization belong to still-higher external components.
- **User-fixed 2026-10-10, exact action granularity:** one undo/redo transaction is **exactly one user action**, not a time-coalesced run of actions. A typed character is its own undo entry; successive typed characters are not merged. One Backspace invocation is one action. A single paste (including multi-line/CSV/2D paste affecting multiple document ranges) is one atomic undo entry. A single input action applied through many carets is one entry covering every affected range. Restore full before/after caret and selection state. Input adapters must preserve semantic user-action boundaries; browser IME/composition behavior still needs concrete integration checks, without inventing timing-based grouping.
- **User-fixed 2026-10-10, simplified persistence boundary (revised for wrapper ownership):** optional history-change observation, if useful, belongs to the external action/history wrapper or a yet more external consumer, **not the low-level editor**. Archival, storage choice, write thresholds and memory-eviction thresholds (e.g. 100 actions to archive, 150 to release) are independent external policies, never part of editing commands. A listener alone cannot free wrapper-owned undo records and enable cold undo; a minimal external release/read-back arrangement would be a separate optional concern and remains undecided.
- **User-fixed 2026-10-10:** persistent history is optional and entirely **outside the low-level editor engine**. A wrapper can provide optional history notifications for an external persistence component; neither the engine nor the foreground action path waits for ordinary persistence. External callers may explicitly wait for synchronization and observe errors/backlog independently from successful text edits. File, browser or network providers and crash recovery remain external; crash durability is not a current requirement.
- **User-fixed 2026-10-10:** sustainable throughput mismatch between external storage and RAM is fundamental and not an editor problem. Background persistence and buffering may absorb temporary bursts, never guarantee that a slower provider keeps up forever. Do not revisit sustained-storage backpressure/retry/throughput as a blocking editor design research task. The reversible-command semantics already tested remain useful evidence for the **external wrapper**, while one input action per history entry and browser input/IME mapping still need integration tests.
- Keep advanced text management and editing semantics decoupled from GUI/browser DOM, so the core architecture could later be translated to C/C++ or another language without redesign, while the GUI may be rewritten independently.
- Prefer a very lightweight DOM view backed by a powerful text object/model rather than using the DOM as the canonical document. The specific rendering/input method remains subject to measurements.
- The historical `m` code is deliberately dirty architectural exploration, not a production baseline or a defect-fix backlog. Preserve insights, not its implementation compromises.
- Browser-embeddable JavaScript remains desirable for reuse across browser, local and optional secure Electron contexts. JavaScript compilation/distribution remains independently owned by the JavaScript toolchain handoff.

## Acceptance scenarios

1. Paste multiline text, a spreadsheet column or CSV-like rows across many existing lines with MadEdit-Mod-like predictable, human-intuitive placement, including unequal source/target line counts, short target lines and mixed character widths; characterize actual expected behavior as executable cases.
2. Make and transform multiple cursors/selections in different 2D/non-linear editing modes, including rectangles, disconnected spans and edits across many lines, without losing text fidelity.
3. Undo/redo complete grouped edits with document contents, cursor positions and selection ranges/direction restored correctly, across repeated long editing sessions without an arbitrary depth cap; test bounded RAM and realistic storage exhaustion behavior.
4. Open, navigate, select, paste and edit realistically very large and long-line documents with stable low memory overhead and responsive viewport interaction; record document sizes, work patterns, latencies and peak memory rather than a generic pass/fail claim.
5. Keep the GUI lightweight and correct under tabs, wide/combining characters, wrapping, scrolling and line numbering, with coherent hit testing and viewport update costs tied to visible content wherever feasible.
6. Run the advanced text core independently of the browser view and embed it in an ordinary browser page or a secure Electron host; verify the core does not assume DOM APIs or renderer-specific state.

## Working design (not normative)

- Compare two main rendering approaches: separate text and left-gutter DOM regions whose alignment is coordinated via CSS/layout/scroll calculations, versus a coordinated DOM structure that gives gutters and editable lines shared layout geometry. Evaluate performance, virtualization, line wrap, scrolling and hit testing before selecting either.
- Compare data structures for huge editable documents (e.g. piece table, rope, balanced indexed tree, piece-tree hybrids), indexing, lazy line geometry and copy-minimizing batch edits; benchmark editing complexity, retained memory, random navigation, Unicode/tabs and long-line behavior before selecting.
- Compare a minimal viewport-only DOM projection with alternative input/rendering strategies; document/editing state must not be mirrored in a full-file DOM. Validate correctness of IME, accessibility, selection hit testing, line numbering and scrolling while minimizing DOM churn.
- Investigate generalized non-linear selection/edit transaction representation separately from any renderer coordinates: document positions, visual columns/virtual spaces and grouped transformations are distinct concerns. Avoid prescribing concrete API/object names before experiments.
- Undo/redo can use compact edit deltas and a generic asynchronous persistence adapter; file, browser and service implementations remain interchangeable provider options rather than core features. Checkpoints are a possible performance optimization for very long normal-session replay, not a crash-recovery obligation now. A potentially unlimited logical history is not a promise of infinite physical storage.
- Examine MadEdit-Mod multiline/column paste semantics with a table of concrete input documents, selection shapes, pasted text, expected output and restored undo state; separate tabular parsing/import behavior from general text placement.
- Compare underlying data and rendering ownership: native DOM/contenteditable versus a controlled document model and separate view/input projection; tradeoffs include column geometry, selection, IME, accessibility, rendering cost and memory.
- Static source review at `m` master `2a57a298`: `m/text/TextEdit.js` holds one string, sorted offset ranges (`start`, `end`, `forward`), mutation listeners and multi-range insertion/removal; `insertText(text, columnMode)` distributes newline-separated input over existing ranges. It does not derive rectangles from visual coordinates, support virtual columns, or define tab/Unicode display-cell geometry.
- **Re-reviewed against the current outer-controller direction (2026-10-10):** the existing `m.text.TextEdit` is a valuable *reference interface* for editor-owned zero-length and oriented multi-range selections plus `modifyText` / `insertText` / `removeText`. The old UI test used `modListeners` to reconstruct one primitive edit's previous text, demonstrating why undo capture needs exact old content, **not** why the low-level editor needs listeners. Current user suggestion is to remove listeners from the editor entirely and let the external controller consume explicit command results; decide exact result/chaining behavior by a narrow proof, retaining fluent `return this` where useful. Do not promote PoC `EditorCore` naming instead of this existing interface. Distinguish implementation defects (`getSelectionRangesCopy` undeclared variable, overlap/bounds checks, unnotified deletion by `collapseSelectionRange`, negative-range hazards) from actual interface gaps (compound atomic command/result, exact old content and selection snapshots, direction's unintended coupling to text reversal, clipboard mapping embedded inside `insertText`). Retain old code as historical reference, not product baseline.
- **Selection-driven architecture viability (working analysis, 2026-10-10):** oriented selections plus atomic, per-target replacement can express any finite set of **non-overlapping document-range replacements** (multicaret typing, disjoint search/replace, prefixing/suffixing rows, paste columns and tabular transformations) when an external controller computes target selections and source-to-target payloads. This is a strong reusable core, **not** proof of literally arbitrary editing. The core must preserve selection identity/order or association even if intervals are sorted, support exact inverse/selection results and deterministic conflict handling for overlaps/duplicate carets; geometry/virtual EOL, tab stops, graphemes and missing destination lines require an external position/row materialization policy. Selection direction (`forward`) is mandatory input to the higher-level selected implementation: it can choose text reversal, a changed placement, or other explicit behavior. Do not hardcode one universal meaning in base. The simple `columnMode` bool conflates clipboard source format, source-to-target line distribution and rectangle geometry: e.g. 2 source rows across 3 selections are padded with an empty string by old `m` whereas VS Code documents full multiline text per cursor when counts differ, and MadEdit-Mod offers optional cyclic autofill for selected column rows. The 3-source/2-destination mismatch is merged into the final target in old `m`, whereas genuine MadEdit-Mod can extend past selected rows. These need test fixtures with precise source/target metadata and normalization, not a core mode switch. A document renderer can consume explicit editor operation results through its external controller instead of subscribing to low-level mutation listeners. Source reviews only; not native MadEdit GUI or full modern-editor behavior parity.
- **Progressive interface decomposition, corrected and tested (2026-10-10):** `TextEditBase` is a **selection-free single-range** text-store contract. Its prototype shape is `length`, `slice(start,end)` for reading and `replace(start,end,text)` for changing exactly *one* interval; **no multi-range primitive belongs in base**. Existing `FlatDocument`, `PieceDocument` and `AdaptiveRepackDocument` satisfy that structural shape with independent backing data. A separate `TextEditSelections` object owns oriented selections/zero-width carets, loops through single-range base operations and maps one string to every selection or an array of strings one-to-one **in user-configured selection order**, not positional sort order. Array length mismatches are rejected. The orientation **MUST be retained and honored**, but each implementation can decide its effect: the PoC injects backward-selection policies (reverse grapheme order versus insertion at the right edge), not one universal behavior, and carries the direction through the resulting selection state. Column geometry/clipboard policy and virtual padding remain above the selection editor and produce the prepared selections and payload array; no `columnMode`. An outer controller independently groups exactly one user action into a history record; listeners, persistence and collaboration remain external. Composition is demonstrated, not an inheritance requirement. Multi-selection rollback above a single-range base is only best effort when the primitive rejects *before* mutating; mutate-then-throw and OOM strong atomicity are unresolved. See the tested PoC source and exact CI below. The API names/methods remain experimental.
- `m/ui/TextEdit.js` is a skeleton; `m/ui/editor.js` is not included in `modules-js.json`. The actual Electron `editor.html` loads a separate host `html/js/editor.js`, while the dynamic library manifest exports the text model and skeletal UI. Thus reference UI/model/selection synchronization is incomplete: the host starts with no model selection ranges and does not project browser selections back into them.

- User clarification (2026-10-10): one Undo reverses one **exact user action**. One typed character is one record, a later typed character another; a single paste is one atomic record even if it changes hundreds of lines or disjoint selection ranges; a single simultaneous multi-caret input is one record. Never coalesce sequential typing by elapsed time. The previously explored `SpillHistory` cold-read behavior is independent of action granularity: with an external archive enabled and older records evicted from RAM, undo at that depth awaits an async provider read; without archival those entries remain in RAM. If the external archive becomes unavailable after eviction, those cold entries cannot be applied until available again. No new runtime test of real input boundaries was executed in this documentation-only correction.

- Superseded interim ownership idea (2026-10-10): undo capacity and a history listener were provisionally assigned to the editor. The **current user direction assigns these to a separate action/history wrapper**; the low-level editor only executes document commands. Independent persistence and memory-release thresholds still belong outside the editing engine. A logical history limit removes undoable actions; evicting records from RAM without losing depth requires an optional external read-back mechanism.

- User-proposed architectural correction (2026-10-10): **remove all undo/redo and history management from the low-level editor**. Introduce a more capable outer object that receives/interprets user input, produces reversible editor-compatible commands and invokes them, and separately owns history, capacity and any notifications. This is a working architectural direction requiring targeted proof, not a claim that a product API or class naming has been adopted. Important correctness question: capture exact overwritten ranges, produce inverse actions only for successfully applied commands, and ensure replay through the same edit entrypoint does not log another user action. Persistence remains outside this separation.

## Current state

Current **user-corrected progressive editing architecture, now experimentally tested**: `TextEditBase` is a structural, low-level, one-interval-only text interface, with NO concept of selections or direction; `TextEditSelections` composes that store, owns zero-size caret selections and oriented ranges, and applies one edit per selected range. The user chooses selection order; one string is replicated, an array maps exactly one-to-one in that order even when physical positions differ. The selection layer MUST honor orientation, but direction's meaning is deliberately implementation-dependent; the PoC supports alternate policies for reverse grapheme order and insertion at a selection's right edge. Column editing is the **next higher layer**, preparing selected targets, virtual padding and per-target payloads. An outer action controller, independently, owns undo/history/optional observation; persistence and collaboration remain external. The earlier rollback-free candidate and its cached execution order have genuine Node benchmark evidence at `28815b3697bbcd2c135ad1059b3403d8bb0d88f3` (run `38079174120`), but **the current selection implementation now includes validated compensating recovery**. Earlier base/selection checks also passed at `e5fdb74343a11b4cdb2f3c47c4e96b3e35f1cbae`. Its full selection hot-path performance is still an open optimization concern, not proven resolved. The previous combined `EditorCore` and action controller experiment remains reference evidence, not the currently preferred layering. The new proof does **not** test actual GUI input, IME or MadEdit-Mod, nor strong atomic failure guarantees for all possible base implementations.

The new external column planner demonstrates model-level 2D clipboard preparation without coupling those policies to either core text layer. Downward new rows beyond EOF are now **opt-in experimentally validated** as grouped regular replacements, including undo inverse replay; other missing-row orientations and native GUI-specific behavior remain open; do not treat a source-derived row-count fixture as full MadEdit-Mod equivalence. The remaining work also includes generalized, DOM-independent 2D/visual geometry: distinguish UTF-16 offsets, grapheme boundaries, view-supplied cell widths, tab stops and virtual EOL columns; detect unresolved positions inside wide glyphs/tabs or colliding selections rather than silently invent policy. The local geometry test passed on two document engines with one grouped multicursor edit and undo/redo. A previous 32 MiB fixture exercised only two short rows while skipping a giant unselected line. New selected-line benchmarks now quantify the enormous cost of materializing full grapheme geometry and an ASCII-prefix-limited candidate that avoids it for that narrow case. The original textarea rectangle's pixel hit testing remains intentionally ASCII/tab-only; a **separate** bounded viewport experiment now has passing real-Chromium hit testing of a few non-bidirectional Unicode grapheme boundaries. This does not validate generalized RTL/complex shaping/variable fonts, seamless viewport input/IME, selected giant-line editing, clipboard behavior on the viewport, mouse drag auto-scroll, or total-memory bounds for file input. A narrowly scoped real Chromium text/keyboard/mouse/clipboard/IME-commit boundary is now tested, not a complete UI editor. Crash recovery is out of scope; JavaScript toolchain ownership is separate.
