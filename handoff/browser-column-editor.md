# Advanced browser/Electron text editor

Status: Active — TextEdit v0.1.0 standalone core released as source and distribution artifact; next focus is GUI integration
Updated: 2026-10-11

## Goal

Design and eventually build an extremely fast, memory-efficient advanced JavaScript text editor capable of handling very large documents while retaining MadEdit-Mod-like intuitive 2D/non-linear editing semantics. Keep a powerful text-management core independent of a lightweight browser DOM UI and usable by optional Electron hosts.

The JavaScript compilation, module loading and distribution concern has **independent ownership** at `handoff/javascript-build-and-runtime-loading.md`. This handoff must not make bundler/loader decisions.

## Fixed task-local choices

- This editor is an independently useful product, not a test fixture for a bundler or an extension of the terminal `vsed`.
- MadEdit-Mod is the starting functional benchmark; its unusually intuitive multiline/Excel-column/CSV paste across many target lines is a defining requirement, beyond generic rectangular selection or multicursor parity. Exact outcomes for differing source/target shapes must be characterized rather than assumed.
- Extreme editing speed, low memory footprint, and responsiveness on very large documents are primary acceptance constraints, not later optimizations. Test realistically rather than promising size-independent latency for operations inherently touching huge ranges.
- Monaco, CodeMirror, Ace and comparable existing editor libraries are excluded as the new editor's engine: inspect their useful concepts/techniques, but do not select or embed them as the editor architecture. PoC 061 remains historical feasibility evidence only.
- Generalize multiple cursors/selections as a foundation for several 2D/non-linear editing modes, rather than implementing only one rectangular-selection special case.
- **User-fixed 2026-10-11, deferred transparent history wrapper:** no listeners and no history inside `TextEditBase` or `TextEditSelections`. Implement history among the final editor features, **not now**. At that stage a wrapper will contain a normal `TextEditSelections` instance and replace it at the caller-facing composition point, preserving the existing selection-editing interface transparently for upper layers and remaining invisible to lower layers. The wrapper alone owns history and undo/redo of complete user actions (including text and selection before/after state). `TextEditBase` remains a selection-free, one-interval text store; higher column-editing planners stay independent, preparing input for the selection interface. No history listeners or cross-cutting interception architecture. Exact implementation and future control entrypoints are deferred; this is a fixed composition choice, not authorization to implement it early.
- **User-fixed 2026-10-10, selections and input scope (compatible with deferred 2026-10-11 wrapper):** the selection-editing layer owns all oriented selections and zero-length cursors; `TextEditBase` owns no selections. Input interpretation stays outside the selection core, and the future transparent history wrapper will delegate selection operations to its contained `TextEditSelections` and restore its before/after state for undo/redo, without becoming the canonical selection owner. Physical keyboards feed one unified ordered logical input stream. Collaboration/synchronization belong above the editor.
- **User-fixed 2026-10-10, exact action granularity:** one undo/redo transaction is **exactly one user action**, not a time-coalesced run of actions. A typed character is its own undo entry; successive typed characters are not merged. One Backspace invocation is one action. A single paste (including multi-line/CSV/2D paste affecting multiple document ranges) is one atomic undo entry. A single input action applied through many carets is one entry covering every affected range. Restore full before/after caret and selection state. Input adapters must preserve semantic user-action boundaries; browser IME/composition behavior still needs concrete integration checks, without inventing timing-based grouping.
- **User-fixed 2026-10-11, no listeners:** do not add mutation listeners, history listeners, subscriptions or change-event hooks to lower text or selection layers, and do not introduce a listener-based cross-cutting history design. History is a late-stage transparent wrapper around `TextEditSelections`. Any optional storage/archival strategy (including memory thresholds and cold undo) is an independent later concern internal to or beyond that future wrapper; it is not part of primitive editing.
- **User-fixed 2026-10-10, deferred persistence (as limited by 2026-10-11 no-listener direction):** persistent history is optional and not part of the lower text or selection engines. Exact persistence, external storage, asynchronous synchronization and crash recovery are postponed until the history wrapper is implemented late in the project. No listener interface is established or required.
- **User-fixed 2026-10-10:** sustained throughput mismatch between external storage and RAM is not an editor-engine problem. The deferred history implementation must not turn provider backpressure or retries into a core editing dependency. The current reversible-command PoCs remain reference evidence only; one user action still corresponds to one history record, and no history mechanism is to be added to the lower layers.
- Keep advanced text management and editing semantics decoupled from GUI/browser DOM, so the core architecture could later be translated to C/C++ or another language without redesign, while the GUI may be rewritten independently.
- Prefer a very lightweight DOM view backed by a powerful text object/model rather than using the DOM as the canonical document. The specific rendering/input method remains subject to measurements.
- The historical `m` code is deliberately dirty architectural exploration, not a production baseline or a defect-fix backlog. Preserve insights, not its implementation compromises.
- Browser-embeddable JavaScript remains desirable for reuse across browser, local and optional secure Electron contexts. JavaScript compilation/distribution remains independently owned by the JavaScript toolchain handoff.

## Acceptance scenarios

1. Paste multiline text, a spreadsheet column or CSV-like rows across many existing lines with MadEdit-Mod-like predictable, human-intuitive placement, including unequal source/target line counts, short target lines and mixed character widths; characterize actual expected behavior as executable cases.
2. Make and transform multiple cursors/selections in different 2D/non-linear editing modes, including rectangles, disconnected spans and edits across many lines, without losing text fidelity.
3. Undo/redo complete grouped edits with document contents, cursor positions and selection ranges/direction restored correctly, across repeated long editing sessions without an arbitrary depth cap; test bounded RAM and realistic storage exhaustion behavior.
4. Open, navigate, select, paste and edit realistically very large and long-line documents with stable low memory overhead and responsive viewport interaction; record document sizes, work patterns, latencies and peak memory rather than a generic pass/fail claim.
5. Keep the GUI lightweight and correct under tabs, wide/combining characters, wrapping, scrolling and line numbering, with coherent hit testing and viewport update costs tied to visible content wherever feasible.
6. Run the advanced text core independently of the browser view and embed it in an ordinary browser page or a secure Electron host; verify the core does not assume DOM APIs or renderer-specific state.

## Working design (not normative)

- **Projection metadata source-map rebase experiment (2026-10-11, candidate only):** preserve the separation already demonstrated between source text, read-only GUI-independent document representation and advanced-selection semantics. New `src/projection-metadata-rebase-probe.mjs` records fold line-boundary anchors and annotation UTF-16 source positions *before* a confirmed `TextEditSelections.replace`, and rebases them *after* using its existing explicit `changes` return and the modified indexed document. No listeners, history, implicit update hooks, GUI, pixel geometry or base/selection changes. An insertion at an annotation anchor requires explicit before/after affinity; anchors replaced or deleted are unresolved. Fold coordinates are retained across edits before the fold **only if both document line boundaries remain verifiably aligned**; folds edited internally or structurally damaged are unresolved, including last-line EOF mutations. The caller constructs a fresh projection from the returned metadata. This is not a source revision tracking mechanism: untracked equal-length edits cannot be detected from the present primitive `TextEditBase` interface. Do not invent a low-level version counter or listener to hide this limitation. Validate whether anchor affinity and conservative fold invalidation are adequate before promoting any representation API. Nested folds, semantic reparse, grapheme-affinity selection and cache invalidation remain open.

- **GUI-independent document representation experiment (2026-10-11; candidate only):** the user's revised direction is a structured representation *of* the source document, shared by rendering clients and advanced selection interpretation, not just a coordinate adapter. Source text remains in the indexed text store. The representation exposes bounded source-referenced text fragments, grapheme boundaries only on complete fragments, fold placeholders mapping one displayed item to multiple hidden source rows, annotation widgets anchored to source offsets but not actual text, and source/view-row mapping. Geometry in fonts/pixels, Unicode text segmentation, content folding, note ownership and semantics of visible-line selections remain distinct. **Advanced selection policy** consumes this representation and prepares ordinary oriented UTF-16 selections; it does not belong inside the representation or in `TextEditSelections`. No GUI, listener or history integration in this phase. The current `src/document-projection-probe.mjs`, `src/advanced-selection-probe.mjs` and `tests/document-projection-probe.mjs` under PoC 063 demonstrate this narrow candidate without promoting class names or output shapes. Source edits require explicit projection reconstruction with rebased fold/note metadata; nested folds, incremental cached invalidation, arbitrary selected giant-line geometry, text wrapping/pixel layout and note editing remain unresolved.

- Compare two main rendering approaches: separate text and left-gutter DOM regions whose alignment is coordinated via CSS/layout/scroll calculations, versus a coordinated DOM structure that gives gutters and editable lines shared layout geometry. Evaluate performance, virtualization, line wrap, scrolling and hit testing before selecting either.
- Compare data structures for huge editable documents (e.g. piece table, rope, balanced indexed tree, piece-tree hybrids), indexing, lazy line geometry and copy-minimizing batch edits; benchmark editing complexity, retained memory, random navigation, Unicode/tabs and long-line behavior before selecting.
- Compare a minimal viewport-only DOM projection with alternative input/rendering strategies; document/editing state must not be mirrored in a full-file DOM. Validate correctness of IME, accessibility, selection hit testing, line numbering and scrolling while minimizing DOM churn.
- Investigate generalized non-linear selection/edit transaction representation separately from any renderer coordinates: document positions, visual columns/virtual spaces and grouped transformations are distinct concerns. Avoid prescribing concrete API/object names before experiments.
- For future evaluation **only**, compact inverse edit deltas and optional asynchronous history persistence remain possible; history will be a transparent wrapper containing `TextEditSelections`, not a responsibility of `TextEditBase` or `TextEditSelections` and not driven by listeners. Checkpoints, storage-provider details and crash recovery have no current implementation mandate.
- Examine MadEdit-Mod multiline/column paste semantics with a table of concrete input documents, selection shapes, pasted text, expected output and restored undo state; separate tabular parsing/import behavior from general text placement.
- Compare underlying data and rendering ownership: native DOM/contenteditable versus a controlled document model and separate view/input projection; tradeoffs include column geometry, selection, IME, accessibility, rendering cost and memory.
- Static source review at `m` master `2a57a298`: `m/text/TextEdit.js` holds one string, sorted offset ranges (`start`, `end`, `forward`), mutation listeners and multi-range insertion/removal; `insertText(text, columnMode)` distributes newline-separated input over existing ranges. It does not derive rectangles from visual coordinates, support virtual columns, or define tab/Unicode display-cell geometry.
- **Historical reference review (2026-10-10; superseded for future history ownership by the fixed 2026-10-11 transparent wrapper):** the existing `m.text.TextEdit` is a valuable *reference interface* for editor-owned zero-length and oriented multi-range selections plus `modifyText` / `insertText` / `removeText`. The old UI test used `modListeners` to reconstruct one primitive edit's previous text, demonstrating why undo capture needs exact old content, **not** why the low-level editor needs listeners. The 2026-10-10 candidate removed editor listeners and let an external action controller consume explicit command results; the newly fixed 2026-10-11 history design instead wraps `TextEditSelections` transparently, still without listeners; decide exact result/chaining behavior by a narrow proof, retaining fluent `return this` where useful. Do not promote PoC `EditorCore` naming instead of this existing interface. Distinguish implementation defects (`getSelectionRangesCopy` undeclared variable, overlap/bounds checks, unnotified deletion by `collapseSelectionRange`, negative-range hazards) from actual interface gaps (compound atomic command/result, exact old content and selection snapshots, direction's unintended coupling to text reversal, clipboard mapping embedded inside `insertText`). Retain old code as historical reference, not product baseline.
- **Selection-driven architecture viability (working analysis, 2026-10-10):** oriented selections plus atomic, per-target replacement can express any finite set of **non-overlapping document-range replacements** (multicaret typing, disjoint search/replace, prefixing/suffixing rows, paste columns and tabular transformations) when an external controller computes target selections and source-to-target payloads. This is a strong reusable core, **not** proof of literally arbitrary editing. The core must preserve selection identity/order or association even if intervals are sorted, support exact inverse/selection results and deterministic conflict handling for overlaps/duplicate carets; geometry/virtual EOL, tab stops, graphemes and missing destination lines require an external position/row materialization policy. Selection direction (`forward`) is mandatory input to the higher-level selected implementation: it can choose text reversal, a changed placement, or other explicit behavior. Do not hardcode one universal meaning in base. The simple `columnMode` bool conflates clipboard source format, source-to-target line distribution and rectangle geometry: e.g. 2 source rows across 3 selections are padded with an empty string by old `m` whereas VS Code documents full multiline text per cursor when counts differ, and MadEdit-Mod offers optional cyclic autofill for selected column rows. The 3-source/2-destination mismatch is merged into the final target in old `m`, whereas genuine MadEdit-Mod can extend past selected rows. These need test fixtures with precise source/target metadata and normalization, not a core mode switch. A document renderer can consume explicit editor operation results through its external controller instead of subscribing to low-level mutation listeners. Source reviews only; not native MadEdit GUI or full modern-editor behavior parity.
- **Progressive interface decomposition, corrected and tested (2026-10-10; history placement corrected 2026-10-11):** `TextEditBase` is a selection-free, one-interval `length` / `slice` / `replace` store. `TextEditSelections` owns the oriented selection state and translates each selected operation to one primitive base edit. The column planner remains above and outside. A future **transparent history wrapper** will contain and replace `TextEditSelections` at its caller-facing boundary, preserve the same editing/selection interface, and own undo/redo without lower-level history or listeners. That wrapper is explicitly **one of the last capabilities to implement**. Earlier `ActionController`, explicit observers and rollback experiments are evidence only; the current selection implementation already uses compensating rollback. No product API is promoted.
- `m/ui/TextEdit.js` is a skeleton; `m/ui/editor.js` is not included in `modules-js.json`. The actual Electron `editor.html` loads a separate host `html/js/editor.js`, while the dynamic library manifest exports the text model and skeletal UI. Thus reference UI/model/selection synchronization is incomplete: the host starts with no model selection ranges and does not project browser selections back into them.

Mutation callbacks are not an undo/redo transaction history.

Treat these as benchmark candidates to reproduce/verify against the user's Windows MadEdit workflow, not as already adopted editor requirements.
- CodeMirror, Monaco and Ace are technique/reference sources only, not engine candidates. The first-party core and view must be validated with targeted, real benchmarks rather than presumed faster merely because it is custom.

PoC 063 columnPastePlan clips excess source rows and is explicitly *not* MadEdit-Mod-compatible in that case. Source-model tests do not substitute for native MadEdit GUI verification.
- Candidate-only experiments in PoC 063: `ChunkedPieceDocument` reuses bounded insertion sources (4,096 UTF-16 units) and merges contiguous source segments; `CompactHistory` records one edit triple and one after-selection snapshot, deriving inverse offsets for undo. Newly tested `AdaptiveRepackDocument` locally materializes a bounded neighborhood only after a piece-density threshold is reached, reducing piece growth for distributed edits. `CompactHistory` now accepts a storage port; the Node-specific `NodeFileJournal` keeps payload and index bytes in files, allowing arbitrary indexed undo/redo reads without a resident entry array. Neither model is an approved engine or a promise of bounded physical memory, persistent durability, or native MadEdit compatibility.

- User clarification (2026-10-10): one Undo reverses one **exact user action**. One typed character is one record, a later typed character another; a single paste is one atomic record even if it changes hundreds of lines or disjoint selection ranges; a single simultaneous multi-caret input is one record. Never coalesce sequential typing by elapsed time. The previously explored `SpillHistory` cold-read behavior is independent of action granularity: with an external archive enabled and older records evicted from RAM, undo at that depth awaits an async provider read; without archival those entries remain in RAM. If the external archive becomes unavailable after eviction, those cold entries cannot be applied until available again.
