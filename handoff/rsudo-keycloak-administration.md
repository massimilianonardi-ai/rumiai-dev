## Fixed task-local choices

- Preserve the existing 16 legacy Keycloak forwarding operations and their compatibility boundary.
- Reuse the single existing Keycloak rsudo module; private credentials remain on the sudo target and are not carried as argument values, stdout or logs.
- Never infer a server, grant or client authenticator or silently change the explicitly selected JWT signing algorithm.
- Continue K04 incrementally; do not present K05 or K06 as implemented.

## Acceptance scenarios

- An operator with a registered confidential Signed JWT client and protected matching remote key/certificate can acquire, inspect, refresh when issued and revoke a token through rsudo while selecting an explicitly supported signing algorithm.
- Wrong algorithm, untrusted certificate, mismatched key, unsafe paths or failed server authentication fail closed without credential disclosure or unintended store replacement.
- The same public flows pass against real isolated Keycloak 26.7.3 and 26.8.1, including composed SSH/sudo where applicable; evidence identifies exact product/suite revisions.
- A configured confidential client with an external identity-provider-linked user can explicitly exchange one current signed RFC 7523 JWT authorization assertion for a non-admin Keycloak token, without implicit refresh or exposing the assertion/token. Invalid issuer/subject, signature/audience/expiry/replay and disallowed client/IdP selection must fail closed. This scenario passed the upstream, direct public and composed SSH/sudo Keycloak tests, as recorded in the current state and validation evidence.

## Working design state

The server grant is available in the verified configurations, but a local browser and a privileged remote shell have different network namespaces and credential custody. The test used an isolated HTTP user agent and an intentionally uncontacted registered HTTPS callback to verify redirects; it did not prove real interactive browser use or real callback receipt. For native/local applications RFC 8252 discusses external-user-agent and loopback/claimed-URI callbacks as potential inputs; no particular approach has been selected for RumiAI. Preserve server-enforced PKCE and client policy and reject implicit permission elevation.

## Blockers / open questions

- Ed448, `self-signed-tls-client-auth`, federated-JWT refresh/password variants, mTLS-bound Admin REST resource enforcement and other grant families remain pending. Runtime client/IdP allowlist governance and external-provider trust require independent deployment-policy validation.
- Native macOS SecureTransport remains incompatible with the selected PEM client-identity path. A compatible curl passed the cleaned macOS test suite 42076656057. Physical reference-host validation remains unperformed.
- Full K04 authenticated Admin REST transport, non-service-account grant families and multi-host physical validation are still pending.
