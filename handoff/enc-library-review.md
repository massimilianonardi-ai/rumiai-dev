## Fixed task-local choices

- Review proceeds function-by-function rather than rewriting the library wholesale.
- `a2o` and `o2a` keep their current byte<->whitespace-separated-octal responsibility and are to be corrected before continuing the encryption helpers.
- `encoded_file_import` is intended to behave like POSIX `.` for pathname resolution: an operand without `/` is searched through `PATH`; decrypted content is executed in the current shell. Use of `eval` is therefore intentional rather than accidental.
- Authentication must still complete successfully before decrypted content is executed by `encoded_file_import`; exact implementation will be reviewed after the primitive helpers.
- For `encode`/`decode`, an unset or empty passphrase variable delegates passphrase acquisition to GnuPG/Pinentry rather than a RumiAI TTY reader; a non-empty supplied passphrase is delivered to GnuPG through fd 3 and never intentionally placed in GnuPG argv or child environment.
- Payload stdin remains on fd 0. The previous fd remapping was only required because a shell pipeline uses the right-hand command's fd 0; the intended redesign supplies fd 3 directly through a dedicated redirection, avoiding any payload-stdin shuffle.
- Do not rely on `printf` being a shell builtin for secrecy. POSIX specifies `printf` as a standard utility but does not require builtin implementation, so a passphrase must not be passed as a `printf` argument when the contract forbids argv exposure.
- Full `env -i` sanitization is not part of the design: GnuPG/Pinentry legitimately depend on session environment such as HOME/GNUPGHOME and GPG_TTY/TERM/DISPLAY. The supplied passphrase is instead copied into subshell positional state and its source variable is unset before any external process.
- OCB capability selection prefers `--use-ocb-sym`; if absent, `--force-ocb` is used only when independently advertised by `gpg --no-options --dump-options`; otherwise encode fails before consuming plaintext or prompting.

## Working design

- The optional supplied-passphrase shell variable is now fixed as `m_ENC_PASS`. It is intentionally a shell variable and should not be exported; encode/decode still unset their subshell copy before any external process.
- The GnuPG/OpenPGP construction remains AES-256, symmetric OCB AEAD, 64 KiB chunks, iterated-and-salted S2K with SHA-256 at count 65011712, no compression and no symmetric-key cache.
- Interactive passphrase acquisition is now owned by GnuPG/Pinentry. Supplied-passphrase mode uses fd 3 with a here-document; payload stdin remains fd 0.
- Current `decode` intentionally streams; authentication failure may occur after plaintext has already been emitted. Consumers requiring authenticated all-or-nothing data must buffer until status 0.
- Public/internal API classification and the mandatory `enc.lib.sh` operational manual are complete. Remaining task work is validation/closure.
- Proposed `encoded_file_import` design: accept exactly one encrypted-source operand; resolve it through the existing public `core.lib.sh` primitive `pathsearch` instead of duplicating PATH traversal. `pathsearch` already handles explicit pathnames, ordered PATH search, empty PATH components as the current directory, no executable-bit requirement and canonicalized result assignment. Normalize path-resolution failure to import status 1. Buffer the complete `decode` output in shell memory and proceed to `eval` only on decode status 0; then return the evaluated source status. No temporary plaintext file and no `command -v`.
- Because `encoded_file_import` is itself a POSIX shell function, it cannot reproduce the caller's outer positional parameters exactly as dot can; the implementation should avoid exposing its own file operand or plaintext buffer as positional parameters to the imported source. Decrypted input is expected to be valid POSIX shell source text; NUL-bearing binary content is outside this API purpose.
- A candidate multi-file loop using `eval "$( ... )"` was analyzed and is not suitable unchanged. Failures from `pathsearch` or `decode` inside the command substitution become an empty eval operand and are therefore reported as success; the following `shift` also overwrites ordinary non-zero eval status. Passing the decrypted source through `printf '%s\n' "$source"` would additionally expose the full plaintext in argv on implementations where printf is external. With xtrace enabled, the plaintext is exposed in assignment/eval tracing. Finally, code executed by eval can modify the function's positional parameters (for example with `set --`) and therefore corrupt a multi-file iteration, and a top-level `return` inside eval returns from `encoded_file_import` rather than merely from one sourced unit.
- Preferred correction direction: capture the complete resolver+decode command substitution in an outer assignment and test that assignment status before eval. A variable assignment whose value contains a command substitution preserves that substitution's exit status across dash, BusyBox sh and Bash POSIX in auxiliary checks, eliminating the extra plaintext printf and preserving the authentication barrier. Multi-file semantics and xtrace policy remain to be settled before implementation.
- Contract exploration established three distinct models. A one-file function `encoded_file_import file [arg...]` can `shift` the file operand and let authenticated source execute with the supplied positional arguments; function positional parameters are temporary, so modifications do not propagate to the caller, while `return` inside the evaluated source naturally returns from the import function. This closely matches the historical KornShell dot-with-arguments extension described in POSIX rationale, although POSIX dot itself accepts only the file operand.
- A multi-file function taking serialized positional state such as `encoded_file_import "$(quote "$@")" file1 file2 ...` can authenticate all files before execution and evaluate them as one import unit with shared temporary positional parameters. Changes to those parameters can flow between imported files but still do not escape to the caller; `return` from any imported source returns from the whole import unit.
- A generator form `eval "$(encoded_file_import file1 file2 ...)"` executes source in the caller's exact frame, so caller positional parameters are visible and `set --` changes persist. This is the only simple POSIX/no-temp model that preserves caller positional mutation, but it has two hard tradeoffs: `return` is relative to the caller context (and is unspecified when no function/dot context exists), and caller xtrace exposes the complete expanded plaintext in the outer eval command before generated code can disable tracing.
- For generated error status, plain `exit N` is not suitable because it terminates the caller shell, and plain `return N` is context-dependent. A generated subshell command `(exit N)` returns status N from eval without terminating the caller; auxiliary checks passed under dash, BusyBox sh and Bash POSIX. Direct `eval "$(generator)"` must nevertheless buffer/authenticate the complete multi-file source before emitting any plaintext, otherwise a later decode failure can still leave earlier generated source executable.
- The remaining contract choice is therefore explicit: prioritize safe import-function semantics (one-file or aggregate function) versus exact caller positional-parameter mutation (generator+outer eval with documented xtrace/return constraints).
- The user selected the one-file function contract and renamed the function to `encoded_file_eval <file> [arg...]`: the file is resolved/authenticated first, then the function shifts the file operand so the evaluated source sees only the explicitly forwarded arguments. Positional changes made by the source remain local to the function frame, while `return` exits the import/eval function rather than an outer caller.
- A follow-up candidate that prepends a trace marker (`:` or `set -x`) and generates the eval body inside command substitution has a viable core idea, but the exact expression `pathsearch ... || printf ... && $1 && exit 2` is wrong because POSIX `&&` and `||` form left-associative AND-OR lists: the marker and `exit 2` run even when pathsearch succeeds, so decode is never reached on the normal path. Passing `"$@"` as additional operands to `eval` is also wrong because eval concatenates all operands into shell source rather than treating them as positional parameters; this produced a real dash/BusyBox/Bash-POSIX divergence on the generated `return 2` path. The here-document form with quotes around `"$_encoded_file_eval_source"` would make the complete plaintext a quoted command name rather than shell source, while a standalone generated `;` is a syntax error.
- The same generator architecture works if it emits exactly one authenticated eval program: disable xtrace before helper state is built, prepend a constant marker argument, resolve the file, fully capture decode output with status preserved (using a non-newline sentinel if trailing newlines are to be retained), emit only restore+return on lookup/decode failure, and on success emit `shift 2`, the literal trace-restoration command, then the authenticated source. Do not pass `"$@"` as extra eval operands. Auxiliary checks of this corrected pattern passed under dash, BusyBox sh and Bash POSIX for forwarded arguments including spaces, source `return 7`, lookup status 2, decode/auth status 3 with emitted partial plaintext not executed, and caller xtrace restoration before source execution.
- A newer candidate corrected the AND-OR grouping and removed extra eval operands, but still masks decode failure because the nested command substitution ends with a successful `printf '\n%s\n' ':;'`; therefore the surrounding assignment returns 0 even when `decode` returns non-zero, the error-3 branch is never entered, and emitted partial plaintext is subsequently evaluated. Auxiliary dash/BusyBox/Bash-POSIX checks confirmed decode failure returns 0 and executes the partial plaintext. The candidate also executes the trace marker (`$1`, either `set -x` or `:`) inside the command-substitution subshell, so it cannot restore xtrace in the parent shell that runs `eval`; xtrace remains off after success or failure. Unquoted execution of the marker also depends on caller `IFS`; with `IFS=:` the literal `set -x` is treated as a single command name and fails. The marker must therefore be emitted as eval source, not executed in the subshell. The `shift 2; ... :;` sentinel strategy itself is viable and preserves forwarded positional arguments and trailing-newline semantics once decode status is preserved explicitly.
- The latest candidate fixes both of those defects: `_encoded_file_eval_source="$(printf 'shift 2' && decode ...)" || ...` now preserves decode failure because decode is the last command in the nested substitution, and the lookup/decode error branches emit the xtrace marker as eval source before `return 2/3`. Auxiliary checks under dash, BusyBox sh and Bash POSIX passed lookup status 2, decode status 3 with partial plaintext not executed, forwarded arguments including spaces, source `return 7`, source final non-zero status, caller positional restoration, and non-default IFS. One functional defect remains: the success path emits only `_encoded_file_eval_source`, whose prologue is `shift 2;`, but never emits the saved marker (`set -x` or `:`); therefore an initially enabled xtrace remains disabled after successful evaluation. The success program must emit the marker before authenticated source execution, preferably after `shift 2`. Also use the project-standard protected `command -p -- cat` (or avoid cat) so a caller-defined `cat` function cannot intercept or alter decrypted source.
- The next simplified candidate converges success and failure into one generated program: `shift 2`, saved trace marker, then authenticated source or `return 2/3`. This is mechanically sound if the decode-failure assignment targets `_encoded_file_eval_source`; the submitted spelling `encoded_file_eval_source="return 3"` (missing leading underscore) is a critical bug because partial plaintext captured before decode failure remains in `_encoded_file_eval_source` and is then evaluated. With that typo corrected, auxiliary dash/BusyBox/Bash-POSIX checks passed forwarded arguments, source `return 7`, final source status, caller positional restoration, lookup 2, decode 3, and rejection of partial plaintext. Xtrace is restored before authenticated source execution on valid source. Remaining caveat: authenticated source is contractually expected to be valid POSIX shell text; an eval parse error can terminate non-interactive dash/BusyBox sh (while Bash POSIX returns a syntax status), so xtrace restoration cannot be guaranteed for syntactically invalid source. The current candidate also disables xtrace only after `set -- "set -x" "$@"`, which causes an avoidable trace of the technical argument reshaping; prefer `set +x` first when tracing is initially active.
- The latest candidate applies both corrections: xtrace is disabled before technical argument reshaping, the decode-failure assignment correctly overwrites `_encoded_file_eval_source`, and the generated eval program is uniformly `shift 2`, saved trace marker (`set -x` or `:`), then authenticated source or `return 2/3`. Auxiliary execution under dash, BusyBox sh and Bash POSIX passed forwarded arguments with spaces and dollar characters, non-default IFS, source command substitutions/backticks/backslashes, source `return 7`, final `false` status, lookup status 2, decode status 3 with partial plaintext not executed, caller positional restoration, and xtrace restoration after success. No new functional defect was found in the valid-source contract. Command substitution still removes trailing newline bytes from decoded source; this is accepted as a representation difference unless exact byte preservation becomes a requirement. Syntactically invalid authenticated source remains outside the intended valid-POSIX-shell-source contract and may terminate non-interactive dash/BusyBox during eval parsing.
- Analysis of a new candidate implementation found several concrete defects: it references `_encoded_file_import_file` instead of the resolved `_encoded_file_eval_file`; `"$_encoded_file_eval_source"` executes the plaintext value as a command name rather than emitting/evaluating it and can execute unauthenticated partial plaintext after decode failure; error-print branches do not stop generation; shifts inside the command-substitution subshell do not change the parent function's positional parameters; successful eval with initial xtrace off returns 1 because the final test is false; and xtrace is not restored when eval fails or evaluated source executes `return`. The safer implementation direction remains outer assignment from resolver+decode, status check before eval, parent-side `shift`, and xtrace restoration embedded before evaluated source when tracing was originally enabled.

- `encoded_file_edit` is now simplified around the POSIX.1-2024 `pipefail` baseline. Public shape: `encoded_file_edit [--preserve-timestamp] [--] file...`; files are processed sequentially and processing stops on the first non-success while earlier committed files remain committed.
- The function runs in a subshell with xtrace disabled and `set -o pipefail`. Each target is resolved with `pathsearch`, fingerprinted with POSIX `cksum`, and gets exactly one adjacent candidate pathname `${file}.$$`.
- Candidate creation uses noclobber redirection before the pathname is assigned to cleanup ownership. A pre-existing `${file}.$$` therefore makes the call fail without overwriting or deleting that pre-existing file. The EXIT trap removes only a candidate successfully created by the current invocation.
- `cp -p` seeds the candidate from the original before re-encryption. This preserves mode/permission bits including executable bits and preserves owner/group when the caller has the required privileges; inability to reproduce those metadata is a hard failure rather than silent degradation. A source mode that makes the seeded candidate unwritable likewise causes the encode redirection to fail.
- Plaintext never receives a pathname. The edit operation is the direct pipeline `decode < target | vsed | encode > candidate`; `pipefail` prevents decode failure, vsed cancellation/runtime failure, or encode failure from authorizing replacement.
- Before commit, a second `cksum` must match the pre-edit value. This is deliberate best-effort content conflict detection, not locking/CAS and not metadata-change detection. With `--preserve-timestamp`, `touch -m -r target candidate` copies the target's current mtime immediately before replacement; without the option the newly encrypted file keeps its new mtime. ctime is intentionally not preserved.
- Final commit is same-directory `mv -f candidate target`. The function returns 0 only when every requested file is committed and non-zero for invalid invocation, cancellation or any resolution, pipeline, metadata, conflict or commit failure. Signal traps retain signal-derived statuses.
