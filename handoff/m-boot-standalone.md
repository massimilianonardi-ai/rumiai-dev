# m-boot standalone Linux build and bootable-media development

Status: Active
Updated: 2026-11-05

## Goal

Evolve the historically field-used `m-boot` into a standalone, reusable multiboot medium focused primarily on recovery, backup and OS installation: prepare a suitable disk/USB drive once, then add/remove bootable ISO images and other supported payloads by ordinary file copy from compatible hosts, without repeatedly flashing devices, recreating media or requiring host-side privileged imaging tools for each payload. The product builds on Linux x86_64/ARM64 and targets applicable x86_64 BIOS, x86_64 UEFI and ARM64 UEFI machines. Integration into `m` is not a current dependency.

### Acceptance/evidence and early stop rules

- **Evidence levels:** existing source inspection; genuine compiled unit/negative tests; real QEMU synthetic boot with original ISO/kernel and Linux post-kernel marker; real vendor-owned media ID acceptance and installer continuation; actual hardware validation. Report the **specific level** and exact source revision per task. A green CI run is not automatically vendor support.
- **Common invariants:** original ISO source/hash unchanged, read-only source-backed maps or QEMU CD, no full multi-GB vendor ISO copy, no modification to GRUB core/m-boot/main/Ventoy/master, no physical USB writes or destructive installer targets, no Docker requirement. Only lightweight disposable test media; characterize true QEMU accelerator/host architecture. No physical operator test without a new candidate and actual device availability.
- **Fail fast and preserve alternatives:** if firmware safety is not proven, stop only M-04 (K and M-01..03 can proceed). If generic early Linux does not hand over to original init, stop M-04 and vendor M tasks, not K. If K-03 cannot expose CD to Linux guest, stop K vendor work but not F/M. If vendor needs wholesale bespoke initramfs per release, stop adaptation and compare stock Ventoy/GRUB loopback/K. Genuine ISO absent is BLOCKED rather than FAIL.
- **QEMU/KVM realism:** guest optical-drive persistence is a property of virtualizing the **whole guest OS**; this is not a bare-metal ISO-only KVM driver. ARM64 host `vmdev` running x86_64 guest uses TCG, not KVM acceleration. Native x86_64 KVM validation requires compatible host/permissions.
- **Security and portability gates:** EFI map/checksum/GPT GUID give integrity/identity checks, not signature-level authenticity. Potential TOCTOU on source extents, media swaps, Secure Boot/EFI runtime policy, module availability, 39–56 MiB vendor initrd replacement and capacity limits remain unresolved until tested; do not generalize from synthetic x86_64 UEFI.

- **GRUB-source policy (operator 2026-11-03, updated by later same-day correction):** No GRUB 2.04 pin, no rebuilding or patching GRUB kernel/core for the optional m-boot ISO engine. - **Ventoy secondary simplification correction (operator 2026-11-03):** Ventoy is to be consumed as an ISO boot compatibility engine, not as a branded disk installer/layout authority.
