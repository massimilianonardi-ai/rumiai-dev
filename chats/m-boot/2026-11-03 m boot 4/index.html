  • La tua chiavetta USB fisica come sorgente della ISO Proxmox.

  • Un piccolo overlay qcow2 temporaneo per isolare le scritture del guest, senza duplicare il contenuto della chiavetta.

  • QEMU x86_64 UEFI sulla VM Ubuntu ARM64, con 3 GiB di RAM e nessuna installazione di Docker.

Lo script identifica la chiavetta dalla ISO montata, controlla MBOOTDATA ext4 sulla partizione GPT 3 e richiede una conferma esplicita prima di smontarla. Non presuppone che il dispositivo sia /dev/sda.

La pubblicazione del disco di boot è ancora subordinata al test EFI automatico. Il test con la vera ISO Proxmox non è stato eseguito sulla tua VM.

Comandi per Ubuntu ARM64

Esegui questi blocchi nello stesso terminale. Non serve aggiornare o modificare il repository m-boot.

1. Scarica soltanto il disco di boot e lo script

Bash
cd /m/src/git/m-boot

ISO="/run/media/admino/MBOOTDATA/m/boot/iso/proxmox-ve_9.2-1.iso"
TESTDIR="/m/src/git/m-boot-proxmox-direct-qemu"

test -r "$ISO" || { echo "ISO non accessibile"; exit 1; }

mkdir -p "$TESTDIR/bundle"

BASE="https://raw.githubusercontent.com/massimilianonardi-ai/Ventoy/20c4eb9fef2835d28fcce2c198be2bd75ae148d1"

for f in boot-disk.raw.gz SHA256SUMS RAW-SHA256SUMS BUILD-INFO.txt test-result.txt; do
  curl -fL --retry 3 \
    "$BASE/GRUB2/dist/secondary-usb-uefi/$f" \
    -o "$TESTDIR/bundle/$f" || break
done

curl -fL --retry 3 \
  "$BASE/GRUB2/port/run-physical-usb-uefi.sh" \
  -o "$TESTDIR/run-physical-usb-uefi.sh"

2. Verifica i file e i prerequisiti

Bash
(
  cd "$TESTDIR/bundle"
  sha256sum -c SHA256SUMS
)

bash -n "$TESTDIR/run-physical-usb-uefi.sh"

for cmd in qemu-system-x86_64 qemu-img sgdisk lsblk findmnt; do
  command -v "$cmd" || echo "MANCA: $cmd"
done

if ! command -v getfacl >/dev/null || ! command -v setfacl >/dev/null; then
  sudo apt-get install -y acl
fi

lsblk -o NAME,PATH,MODEL,SIZE,TYPE,TRAN,FSTYPE,LABEL,MOUNTPOINTS
df -h "$TESTDIR"
free -h

Il controllo sha256sum deve restituire boot-disk.raw.gz: OK.

3. Avvia QEMU con la USB reale

Bash
bash "$TESTDIR/run-physical-usb-uefi.sh" \
  "$ISO" \
  "$TESTDIR/bundle" \
  "$TESTDIR"

Lo script individuerà il dispositivo fisico dalla posizione della ISO. Dopo aver mostrato le partizioni, chiederà una conferma del tipo:

Type exactly TEST /dev/sda to continue:

Digita il dispositivo effettivamente mostrato, non necessariamente /dev/sda.

Lo script smonterà MBOOTDATA dall'host, assegnerà temporaneamente al tuo utente l'accesso in lettura al dispositivo se necessario, creerà l'overlay e lancerà QEMU. Non formatterà la USB e non copierà Proxmox.

4. Esamina i risultati

Dopo aver chiuso la finestra QEMU:

Bash
find "$TESTDIR" -name qemu.log -print

grep -ahE \
  'VT_USB_|VT_CHAIN_|VT_HANDOFF|VT_MAP_|error:' \
  "$TESTDIR"/mboot-usb.*/qemu.log | tail -n 150 || true

Conserva il qemu.log e dimmi fino a quale schermata arriva Proxmox. Lo script lascia la chiavetta smontata dall'host dopo la prova; puoi rimontare la partizione MBOOTDATA tramite il file manager oppure udisksctl mount -b indicando la partizione identificata da lsblk.

Ho aggiornato anche il checkpoint m-boot in rumiai-dev, registrando gli artefatti pubblicati, i risultati CI e il test Proxmox ancora da eseguire.

Stato finale: disco di boot pubblicato e verificato; procedura di accesso diretto alla USB preparata; m-boot/main, Ventoy/master e chiavetta fisica non modificati da questo lavoro.

Se lo script si ferma durante i controlli del dispositivo, non aggirarli: incollami l'errore. Altrimenti il risultato più utile sarà il qemu.log insieme alla schermata raggiunta da Proxmox.

Ho trovato un punto decisivo nel codice di avvio dell'installer Proxmox: la verifica dell'ISO non avviene mediante una chiamata EFI.

L'initramfs Linux, nella procedura di ricerca documentata dal codice dell'installer, usa /sys/block, blkid e mount per cercare un dispositivo contenente un filesystem ISO9660; poi legge il file .pve-cd-id.txt e confronta il suo contenuto con l'ID atteso. L'interfaccia EFI serve nella fase precedente, per caricare il bootloader, non per questa ricerca.

GitHub+1

Quindi non basta implementare un'altra funzione EFI. La virtualizzazione deve proseguire anche dopo il passaggio di controllo al kernel Linux, rendendo nuovamente accessibile la ISO tramite un dispositivo a blocchi oppure tramite un meccanismo equivalente accettato dall'initramfs.

È esattamente il confine che la nostra integrazione Ventoy attuale non ha ancora attraversato.

La soluzione generale è già presente in parte nel Ventoy originale

Nel fork ho individuato i componenti che ci servono:

Componente

Responsabilità

Mappa i settori fisici della ISO. È già operativo nei nostri test.

VtoyTool/vtoydm.c

Converte la mappa Ventoy in una tabella Linux Device Mapper.

IMG/cpio/ventoy/init_chain

IMG/cpio/ventoy/hook/debian/pve-hook.sh

È significativo che Ventoy abbia già un adattatore specifico per Proxmox. Non dobbiamo ricostruirlo da zero; dobbiamo verificare come riutilizzarlo nel nostro percorso secondario.

Architettura da completare

Il punto mancante è il passaggio EFI → initramfs. Device Mapper e FUSE sono meccanismi Linux, non servizi EFI.

L'obiettivo è riutilizzare la stessa mappa fisica, così da non leggere né copiare interamente la ISO:

ISO su ext4 → extent fisici → Device Mapper Linux → ISO9660 → installer

La specifica UEFI conferma che i protocolli di avvio, compreso BlockIo, non sono utilizzabili dal sistema operativo dopo ExitBootServices.

UEFI Specification 2.10 documentation+1

Il vero problema implementativo

C'è un dettaglio che spiega perché il codice attuale non completa il percorso.

L'implementazione sperimentale probe-handoff.c inizializza i parametri passati a Ventoy ma non prepara la sostituzione dell'initramfs. Invece, il Ventoy completo utilizza vt_load_cpio, vt_trailer_cpio e gli hook sulle letture dei file EFI per far arrivare il proprio codice all'ambiente Linux.

Questo è il meccanismo da portare nel modulo GRUB esterno, mantenendo il core GRUB originale. Non è ancora dimostrato che possa essere integrato interamente senza modifiche al core.

Prossimi passi tecnici

  1. Esaminare l'initramfs effettivo Proxmox 9.2 sulla chiavetta, in sola lettura, verificando il contenuto di /init, i moduli disponibili e il controllo sull'ID. Ho trovato codice dell'installer e un log ufficiale relativo a 9.2, ma non ho ancora esaminato i byte della tua ISO specifica.

  2. Dimostrare la ricostruzione Linux del dispositivo ISO, partendo dalla mappa già ottenuta dal nostro modulo e usando il Device Mapper originale di Ventoy. Verificare il vero filesystem e l'ID, non simularli.

  3. Integrare il passaggio dell'initramfs nel boot UEFI, riutilizzando il meccanismo di sostituzione già presente nel Ventoy originale o valutando, se necessario, un percorso GRUB Linux diretto.

  4. Validare Proxmox e TrueNAS separatamente, fino al montaggio dell'effettivo supporto, senza considerare sufficiente il solo avvio del kernel.
