L'implementazione è suddivisa in quattro parti.

1. Lettura dell'input

La shell gestisce gli argomenti, legge da standard input o da file e utilizza od per convertire il contenuto in una sequenza di byte numerici.

Questo permette di analizzare anche input contenenti byte non validi, caratteri NUL o sequenze UTF-8 malformate, senza perderli durante la lettura.

2. Analisi lessicale (lexer)

AWK legge i byte uno alla volta e riconosce:

  • Stringhe, escape e sequenze Unicode \uXXXX.

  • Numeri, compresi frazioni ed esponenti.

  • Valori true, false e null.

  • Delimitatori {}, [], , e :.

Controlla inoltre la validità delle sequenze UTF-8.

I numeri non vengono convertiti: vengono mantenuti esattamente come nell'input, evitando problemi di precisione.

3. Analisi sintattica (parser)

Il parser utilizza una macchina a stati con uno stack esplicito, implementato mediante array associativi AWK.

Per esempio, un oggetto attraversa gli stati:

inizio oggetto
    ↓
attesa chiave
    ↓
attesa :
    ↓
attesa valore
    ↓
attesa , oppure }

Gli array seguono una macchina a stati analoga.

Questo approccio offre due vantaggi importanti:

  • Nessuna ricorsione: gestisce annidamenti molto profondi senza consumare lo stack delle chiamate della shell.

  • Validazione completa: verifica tutto il documento, non soltanto i valori che interessano.

4. Produzione dell'output

Il parser può funzionare in due modalità:

ModalitàComportamento
jsonValida e restituisce JSON compatto
json -cValida senza produrre output

L'output viene prima scritto in un file temporaneo privato e pubblicato soltanto se l'intero documento è valido.

Quindi un errore alla fine dell'input non provoca la restituzione di JSON parziale.

Caratteristiche e compromessi

Vantaggi

  • Portabilità POSIX.

  • Nessuna dipendenza da runtime esterni.

  • Supporto UTF-8 e grammatica JSON completa.

  • Nessuna perdita di precisione numerica.

  • Annidamento non ricorsivo.

  • Superamento dei 283 test obbligatori di JSONTestSuite.

Limiti

  • od introduce una conversione intermedia, con un costo prestazionale.

  • L'input viene materializzato in file temporanei.

  • Attualmente il comando valida e compatta, ma non offre interrogazioni o trasformazioni strutturali.

In sintesi: è un vero parser JSON a stati, non una soluzione basata su espressioni regolari o sostituzioni testuali. La shell gestisce l'esecuzione, mentre AWK implementa il lexer e il parser.

3. La command line di jq

La scelta principale di jq è avere un'espressione di interrogazione come argomento, seguita dai file da elaborare.

Bash

Se non viene specificato un filtro, il comportamento predefinito è equivalente a ..

Il filtro non è soltanto un percorso: è un'espressione che riceve un valore JSON e può restituire zero, uno o più valori. Questa caratteristica è fondamentale. jqlang.org

4. Contratto CLI proposto per json

Propongo di adottare la struttura di jq, mantenendo il comando autonomo e POSIX.

Invocazione

json [options] [filter] [file...]
json --check [file...]

Il filtro predefinito è .. In presenza di un file e senza altre opzioni, si usa esplicitamente il filtro:

Bash
json . config.json

Il trattino - come operando file indica lo standard input. -- termina l'interpretazione delle opzioni, come in jq.

Esempi operativi

Estrarre una proprietà:

Bash
json -r '.user.name' config.json

Estrarre un elemento di array:

Bash
json '.servers[2].host' config.json

Estrarre più valori:

Bash
json -r '.servers[].host' config.json

Selezionare elementi in base a una condizione:

Bash
json -c '.users[] | select(.age >= 18)' users.json

Validare senza stampare nulla:

Bash
json --check config.json

L'ultima forma è un'estensione RumiAI rispetto a jq, utile per conservare la funzionalità di validazione già realizzata.

Semantica che raccomando

Input: leggere dallo standard input oppure dai file indicati. Come jq, il flusso può contenere più valori JSON successivi, elaborati individualmente.

Output: un risultato JSON per ogni valore prodotto dal filtro. Formattazione leggibile per impostazione predefinita; -c per quella compatta; -r per estrarre il contenuto delle stringhe.

Valori mancanti: seguire jq. Per esempio, .missing su un oggetto restituisce null, mentre .[] su un array vuoto non produce risultati.

Chiavi Unicode: confrontare i nomi dopo la decodifica degli escape. {"a":1} e {"\u0061":1} devono comportarsi nello stesso modo durante un'interrogazione per la chiave a.

Chiavi duplicate: propongo il comportamento di jq: quando più proprietà hanno lo stesso nome, prevale l'ultima nella rappresentazione dell'oggetto. Questo cambia l'attuale comportamento di semplice conservazione testuale e va trattato esplicitamente.

Errori: distinguere filtro malformato, JSON non valido, errore di accesso, errore di esecuzione e assenza di risultati. Con -e raccomando i codici di jq 0, 1 e 4 rispettivamente per risultato finale vero, false/null e nessun risultato. Questo richiede di riallineare i codici attuali, perché 4 oggi indica un errore lessicale. jqlang.org

Quale porzione di jq implementare?

Qui distinguerei due livelli.

Primo livello: interrogazioni strutturali. Comprende selezione di proprietà, indici, iteratori, concatenazione di percorsi, |, , e accesso opzionale. È la parte che rende il comando immediatamente utile e supera entrambi i progetti di riferimento.

Secondo livello: filtri espressivi. Comprende select, confronti, operatori logici, costruzione di array e oggetti, map, keys, length, has e variabili.

Sconsiglio di promettere subito compatibilità completa con il linguaggio jq: significherebbe implementare un linguaggio di programmazione, non soltanto un parser JSON. Un sottoinsieme dovrebbe essere dichiarato precisamente, e le espressioni non supportate dovrebbero generare errore, senza comportamenti approssimativi.

5. Implicazioni sull'implementazione attuale

Il parser già realizzato può essere riutilizzato, ma deve cambiare l'organizzazione interna.

Attualmente:

Input JSON
    ↓
Lettura byte
    ↓
Lexer
    ↓
Validazione sintattica
    ↓
Compattazione
    ↓
Output

La nuova organizzazione dovrebbe essere:

                      Espressione filtro
                              ↓
                        Parser del filtro
                              ↓
Input JSON → Lexer → Parser JSON → Motore di interrogazione
                                         ↓
                                  Serializzazione
                                         ↓
                                       Output

La differenza sostanziale è che oggi il parser verifica la struttura, ma non espone al resto del programma quali valori appartengono a quali percorsi.

Per le interrogazioni occorrerà quindi produrre una rappresentazione navigabile oppure eventi strutturali sufficienti per valutare i filtri.

Non serve necessariamente caricare tutto il JSON in memoria: per le interrogazioni per percorso si può elaborare la struttura progressivamente, mantenendo i riferimenti agli oggetti e agli array pertinenti. Filtri più complessi, invece, potrebbero richiedere di memorizzare interi sottoalberi.

Va inoltre rivista l'attuale garanzia di output completamente atomico: è utile per un validatore, ma la materializzazione di tutto il risultato può penalizzare l'elaborazione di grandi flussi JSON.
