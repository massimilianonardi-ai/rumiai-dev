3.3 Client Admin API

Un'unica responsabilità gestisce le richieste HTTP.

Riceve:

metodo HTTP
tipo di risorsa
identificatore eventuale
corpo JSON eventuale

Produce:

risposta APISIX su stdout
diagnostica su stderr
status di esecuzione

Il client deve:

  • verificare il codice HTTP, non soltanto il codice di uscita di curl;

  • distinguere gli errori SSH, sudo, HTTP, autenticazione APISIX e validazione;

  • trasmettere il corpo JSON senza interpolarlo in codice shell;

  • applicare timeout espliciti;

  • gestire correttamente i caratteri speciali negli identificatori;

  • mantenere separati risposta e metadati diagnostici;

  • evitare modifiche implicite o tentativi di correzione distruttivi.

La validazione sintattica JSON può riutilizzare il comando json --check già disponibile in rumiai-os. La validazione semantica specifica delle risorse resta affidata ad APISIX.

Il client remoto utilizzerà curl, dichiarato come dipendenza operativa, senza richiedere l'installazione di m sul server.

3.4 Configurazione, autenticazione e sicurezza

Preferirei che il modulo comunicasse con l'Admin API dal server remoto, utilizzando normalmente l'interfaccia locale.

APISIX documenta come indirizzo predefinito:

http://127.0.0.1:9180/apisix/admin

Endpoint e porta sono configurabili. L'API utilizza normalmente la chiave trasmessa nell'header X-API-KEY. Apache APISIX

L'architettura deve prevedere una risoluzione esplicita di:

  • endpoint amministrativo effettivo;

  • modalità di deployment;

  • sorgente autorizzata delle credenziali;

  • privilegi disponibili;

  • capacità supportate dalla versione installata.

Non considero corretto presumere che APISIX sia sempre installato in un percorso fisso.

In particolare, le chiavi amministrative non dovrebbero essere stampate, incluse nei log o trasmesse inutilmente alla macchina che esegue il job.

La soluzione privilegiata è utilizzare credenziali già disponibili e protette sul server remoto, prevedendo alternative esplicite per installazioni che le gestiscono diversamente.

Anche l'invocazione del client HTTP deve essere progettata per evitare, per quanto possibile, che la chiave compaia negli argomenti osservabili dei processi.

3.5 Modalità di deployment

Non tutte le installazioni APISIX sono amministrabili allo stesso modo.

APISIX distingue, fra le altre, modalità tradizionale, control plane/data plane separati e configurazione standalone. Nelle installazioni standalone basate su file non si utilizza il normale percorso amministrativo basato su etcd. Apache APISIX

Propongo quindi questo limite iniziale:

Prima implementazione: amministrazione attraverso l'Admin API standard nelle installazioni che la espongono.

La gestione standalone, la pubblicazione completa della configurazione e il lifecycle dei processi APISIX devono essere considerati responsabilità differenti, da integrare solo dopo averne verificato i rispettivi contratti.

Questo evita di mescolare amministrazione delle risorse e deployment del servizio.

6.3 Problemi principali individuati

A. Costruzione delle richieste HTTP

L'attuale rsudo_mod_apisix_api() genera dinamicamente comandi curl attraverso una heredoc.

Il contenuto JSON viene interpolato direttamente nel codice shell remoto.

Questo introduce problemi di quoting e potenziali vulnerabilità di command injection quando i dati contengono caratteri speciali.

Correzione proposta: codice remoto statico, parametri trattati come dati e corpo JSON trasmesso attraverso stdin.

B. Percorsi REST non corretti

Diverse funzioni di creazione invocano PUT sulla collection, per esempio:

PUT /apisix/admin/upstreams

La normale creazione o sostituzione con identificatore esplicito utilizza invece:

PUT /apisix/admin/upstreams/{id}

La creazione senza identificatore può utilizzare il metodo POST dove previsto dall'API.

La stessa distinzione è importante per route e service. Apache APISIX

L'attuale implementazione non distingue correttamente queste semantiche.

C. Gestione delle chiavi amministrative

La funzione rsudo_mod_apisix_key() estrae la chiave da:

/usr/local/apisix/conf/config.yaml

utilizzando una sequenza di sed.

I problemi sono significativi:

  • percorso di installazione fisso;

  • parsing testuale fragile di YAML;

  • impossibilità di selezionare correttamente diverse configurazioni amministrative;

  • trasferimento della chiave dal server al processo locale;

  • successivo inserimento della chiave in un comando HTTP.

Preferisco la risoluzione delle credenziali direttamente sul server remoto, secondo la reale configurazione APISIX.

D. Controllo degli errori

Il modulo utilizza curl -i senza una gestione esplicita degli status HTTP.

Di conseguenza, una risposta HTTP 400, 401, 403 o 500 può essere interpretata come successo dal chiamante quando il trasferimento HTTP è terminato correttamente.

Inoltre, gli header HTTP vengono mescolati con il corpo della risposta.

Dobbiamo separare correttamente questi risultati.

E. Generazione JSON

La funzione rsudo_mod_apisix_json_string_or_array() utilizza:

Bash
set -- $1

Questo comporta word splitting e potenzialmente pathname expansion.

Inoltre, il codice costruisce JSON concatenando stringhe senza un escaping generale affidabile.

La nuova implementazione deve distinguere chiaramente i dati JSON già validati dalle stringhe che devono essere serializzate.

F. Accoppiamento APISIX/Keycloak

La funzione rsudo_mod_apisix_set_auth_vars() configura contemporaneamente APISIX e Keycloak.

Le configurazioni dei plugin sono poi costruite attraverso template che interpolano variabili shell.

Questa soluzione rende difficile riutilizzare il modulo con altri identity provider.

Inoltre, il valore predefinito del session secret richiede una correzione dal punto di vista della sicurezza.

G. Completezza funzionale

Attualmente manca un'interfaccia CRUD uniforme.

Il modulo contiene numerose funzioni specializzate per eliminare risorse, ma non dispone di un insieme equivalente e coerente per elencare, leggere, creare, modificare e cancellare tutte le tipologie supportate.

L'infrastruttura HTTP è presente, ma non costituisce ancora un client amministrativo completo.

H. Diagnostica e documentazione

Alcune funzioni condividono status generici per errori differenti.

In rsudo_mod_apisix_create_route_map() è presente anche una chiamata log fatal incondizionata, apparentemente utilizzata durante lo sviluppo.

Manca inoltre il manuale della libreria APISIX richiesto dall'architettura corrente e non risultano test permanenti specifici del modulo APISIX.
