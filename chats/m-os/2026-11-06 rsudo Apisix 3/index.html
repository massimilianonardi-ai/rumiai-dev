0. Decisioni architetturali

Queste decisioni costituiscono il punto di partenza del nuovo piano.

  1. La discovery è responsabilità del modulo. Deve trovare e descrivere le istanze APISIX osservabili sul sistema remoto, senza pretendere di identificarne perfettamente ogni dettaglio.

  2. La selezione dell'istanza è responsabilità dell'utente. L'utente sceglie il sistema, l'istanza e il deployment mediante variabili d'ambiente. Il modulo non decide automaticamente quale istanza amministrare.

  3. La discovery non modifica l'ambiente. Produce un inventario informativo. Può eventualmente generare suggerimenti per impostare le variabili, ma non le imposta autonomamente.

  4. Il deployment selezionato determina il backend amministrativo. Il modulo utilizza il backend specificato nell'ambiente, eventualmente verificandone la coerenza con le informazioni osservabili.

  5. L'API pubblica è unica. Le operazioni list, get, create, update, delete e le funzioni specializzate mantengono la stessa interfaccia indipendentemente dal backend.

  6. Il routing è interno alla libreria. Non si creano moduli pubblici diversi per REST, YAML, JSON ecc. Le implementazioni possono essere organizzate in funzioni private all'interno di rsudo-mod-apisix.lib.sh.

  7. La sicurezza è locale all'operazione. Non si richiede una certificazione universale dell'istanza prima di procedere. Si controlla invece che l'operazione scelta sia indirizzata correttamente e possa essere eseguita senza corrompere dati o compromettere credenziali.

  8. Il vecchio modulo resta disponibile come apisixlegacy. Nessuna migrazione implicita verso le vecchie implementazioni quando un'operazione nuova non è supportata.

  9. Le funzionalità vengono consegnate progressivamente. Discovery, configurazione, letture e scritture vengono sviluppate e validate in unità autonome, senza rimandare tutto al completamento dell'intera ricerca.

  10. Si riutilizzano le funzionalità già disponibili. Parser APISIX, osservazione processi, trasporto rsudo, test esistenti e interfacce legacy vengono valutati prima di scrivere codice nuovo.

1.1 Livello di discovery

Ingresso:

Usa esclusivamente l'ambiente di connessione rsudo, senza richiedere che sia già selezionata un'istanza APISIX.

Restituisce un insieme di candidati:

  • installazioni rilevate tramite filesystem;

  • processi APISIX effettivamente in esecuzione;

  • container Docker e Podman;

  • servizi associabili ad APISIX;

  • porte e endpoint dichiarati nei file di configurazione;

  • risultati dei controlli di raggiungibilità;

  • indicazioni sulla modalità di deployment;

  • problemi, incertezze e informazioni non disponibili.

Una singola esecuzione può restituire zero, una o molte istanze.

1.2 Livello di contesto

Legge variabili d'ambiente scelte dall'utente, valida i valori e costruisce un unico oggetto logico interno contenente:

  • sistema remoto rsudo;

  • tipo di esecuzione: host, Docker o Podman;

  • identificativo del processo o container, quando pertinente;

  • percorso dell'installazione;

  • percorso della configurazione;

  • ruolo e modalità di deployment;

  • backend amministrativo;

  • endpoint amministrativo o documento da modificare;

  • riferimenti alle credenziali.

Non esegue una nuova discovery completa per ogni comando.

1.3 Livello API

Riceve richieste indipendenti dal backend:

list, get, create, update, delete, apply, request.

Convalida la risorsa, l'operazione, il payload e i prerequisiti.

1.4 Router

Sceglie la funzione privata corretta in base al contesto esplicito:

  • REST Admin API;

  • REST standalone snapshot;

  • file YAML;

  • file JSON;

  • backend non amministrabile direttamente.

1.5 Backend

Traducono l'operazione astratta nella corrispondente operazione APISIX, mantenendo le differenze di comportamento necessarie.

1.6 Risultato

Restituisce un risultato JSON coerente, con dati, metadati e stato dell'operazione. Gli errori e i diagnostici sono separati su stderr.

15. Definizione di prodotto completo

Il task rsudo apisix potrà essere dichiarato concluso quando saranno vere tutte le seguenti condizioni:

  • discovery individua e descrive correttamente le installazioni supportate, incluse più istanze e istanze non attive.

  • L'utente può selezionare un'istanza tramite variabili d'ambiente.

  • La scelta dell'istanza è indipendente dalla discovery.

  • Il routing interno sceglie correttamente il backend.

  • list/get restituiscono risultati utilizzabili sulle modalità certificate.

  • CREATE, UPDATE e DELETE funzionano sulle modalità amministrabili supportate.

  • Gli aggiornamenti file e snapshot non compromettono configurazioni estranee.

  • Le API semplificate permettono di amministrare upstream, service e route senza preparare file JSON.

  • Le credenziali e i dati vengono trasportati in modo sicuro.

  • Le funzionalità sono coperte da test permanenti con APISIX reale.

  • apisixlegacy rimane isolato e funzionante per le compatibilità previste.

  • Specifiche, manuali, implementazione e test sono coerenti.

  • Non restano backend dichiarati supportati ma privi della relativa validazione.

La discovery è una funzione del prodotto. La configurazione dell'ambiente è una responsabilità dell'utente. L'amministrazione multi-backend è la responsabilità principale del nuovo modulo.
