# RumiAI OS — Filesystem Naming Convention

Status: **Normative specification**  
Date: 2026-08-28

## 1. Scope

This specification defines naming rules for filesystem objects whose names are controlled or automatically generated by RumiAI or by RumiAI tools.

It does **not** restrict names explicitly supplied by a user or names originating from external tools, filesystems or datasets. Such names are external data and must be handled safely as opaque pathnames.

The purpose is to keep RumiAI-controlled names predictable, portable and simple enough that bootstrap and internal tooling do not need defensive handling for arbitrary filename syntax that RumiAI itself would never generate.

Normative baseline:

**POSIX.1-2024 / The Open Group Base Specifications Issue 8**.

---

## 2. RumiAI-controlled names

Unless an explicit documented exception applies, every pathname component created and named by RumiAI MUST:

- use only lowercase ASCII letters `a-z`, digits `0-9`, period `.`, underscore `_`, and hyphen `-`;
- start with a lowercase ASCII letter or digit;
- end with a lowercase ASCII letter or digit;
- contain no whitespace;
- contain no control characters, including newline, carriage return or tab;
- not begin with `-`;
- not be `.` or `..`.

Default shape:

```text
[a-z0-9][a-z0-9._-]*[a-z0-9]
```

with a single-character name `[a-z0-9]` also valid.

This is intentionally stricter than the POSIX portable filename character set.

## 3. Word separation

For human-readable multiword RumiAI-controlled names, hyphen `-` SHOULD be the default word separator:

```text
rumiai-os
package-cache
bootstrap-state
```

Underscore `_` MAY be used where it has an established semantic or machine-oriented purpose, but SHOULD NOT replace hyphen merely as an alternate visual style.

## 4. Executable commands

Public executable command names follow the existing RumiAI command-naming rule:

- semantic name;
- lowercase;
- no extension that exposes the implementation language;
- conventionally hyphen-separated when multiword.

Canonical example:

```text
rumiai-os
```

## 5. Semantic extensions

Non-executable files MAY use semantic extensions when the extension describes their role or actual source format.

Examples already accepted by the project include:

```text
.lib
.conf
.c
.cpp
.java
.js
```

An executable does not gain `.sh`, `.py`, `.js` or a similar suffix merely because that is its implementation language.

## 6. Semantic identifiers used as pathname components

A pathname component that intentionally encodes an identifier governed by a separate semantic convention MAY depart from the default lowercase naming form when preserving that identifier is valuable.

The first accepted case is the RumiAI language identifier, whose current language/territory form is:

```text
language_TERRITORY
```

Examples:

```text
en_US
it_IT
```

Therefore language directories under `lang/` MAY use this form and the uppercase territory component is intentional rather than an accidental violation of the generic naming convention.

Whether the character encoding/codeset is also part of this identifier or of the corresponding language-directory name is intentionally **not yet decided**. Forms such as:

```text
it_IT
it_IT.UTF-8
```

remain under architectural evaluation until the i18n encoding contract is fixed.

Semantic exceptions MUST be documented by the subsystem that owns the identifier and MUST NOT become a general excuse for arbitrary naming variation.

## 7. Hidden and conventional names

A leading period is reserved for cases where hidden-file semantics are intentional and explicitly specified.

Conventional ecosystem names that do not follow the default lowercase rule MAY be adopted explicitly where their conventional identity is useful. The existing root file:

```text
README.md
```

is such an accepted exception.

Exceptions MUST be deliberate rather than accidental.

## 8. User and external names

Names supplied by users or external tools are outside the RumiAI-controlled naming convention.

RumiAI MUST NOT silently rename, lowercase, trim or otherwise normalize such names merely to make them conform to this specification.

External pathname data MAY therefore contain spaces, newlines, leading hyphens, non-ASCII bytes or other POSIX-valid filename content.

Code handling external pathnames MUST:

- treat them as data;
- quote expansions correctly;
- use supported option delimiters where required by the canonical `--` rule;
- avoid parsing human-oriented utility output to recover pathname data.

If a RumiAI tool automatically generates a new internal name from external/user data rather than preserving the supplied name, the generated name MUST follow this convention and the transformation/collision policy must be explicit for that tool.

## 9. Bootstrap consequence

The canonical product entrypoint name is fixed as:

```text
rumiai-os
```

and is a RumiAI-controlled name. Therefore its final pathname component cannot contain a trailing newline.

Phase 0 may safely capture `command -v` and `realpath` output with ordinary POSIX command substitution without a sentinel protocol for trailing-newline preservation:

- `command -v` resolves the fixed command name `rumiai-os` when invoked through `PATH`;
- `realpath` returns a canonical pathname whose final component is the controlled product entrypoint;
- newline characters in externally controlled parent directory components are embedded within the pathname, not trailing output bytes, and are preserved by command substitution.

A user-created external symlink may itself have an arbitrary name; direct `$0` assignment preserves it before `realpath` canonicalizes it to the controlled product entrypoint.

The more general fact that POSIX command substitution removes trailing newline bytes remains relevant for arbitrary external pathname-producing workflows, but it is not a requirement of the phase-0 bootstrap implementation.
