# RumiAI OS — testlab

Status: **Current / normative**  
Updated: 2026-09-29

This specification defines the first current contract of the `m` developer-facing live scenario environment command `testlab`.

## 1. Responsibility

`testlab` belongs to the technical `m` substrate.

Its responsibility is to create or bind a concrete development scenario, persist enough lifecycle state to recover and close that scenario after interruption, expose factual context to activities, and permit direct interactive use of a ready instance.

`testlab` is not a test runner, assertion engine or formal-validation launcher. It does not replace:

```text
rumiai-test
rumiai-validate
*.test assertions
```

A testlab scenario may later be consumed by a manual activity, a development command, a PoC or a permanent test, but those activities retain their own semantics.

## 2. Project-local scenario definitions

The first baseline discovers scenarios from the current project root:

```text
<project-root>/testlab/scenarios/<scenario>
```

The project root is the physical current working directory at `testlab` invocation. The baseline does not search parent directories, a global registry or `res/` for scenarios.

A scenario leaf:

- follows the controlled-name grammar;
- is a regular executable file;
- is not a symbolic link;
- is trusted project development code.

Scenario definitions are executed as child programs. They are never sourced into the `testlab` shell process.

The first baseline deliberately introduces no scenario DSL, resource graph, provider/plugin framework or activity/assertion language.

## 3. Scenario phase interface

A scenario executable accepts one of these phase operands:

```text
check
prepare
enter
cleanup
```

The generic lifecycle is:

```text
check
    validate prerequisites before testlab allocates persistent instance state
    or the scenario performs runtime mutation

prepare
    create or bind concrete resources
    persist ownership information immediately as resources are created/bound
    establish readiness
    publish context facts

enter
    attach the operator directly to the already-prepared scenario
    using the normal inherited terminal/standard streams

cleanup
    release the instance and remove only resources recorded as testlab-owned
    by that scenario
```

`check` receives any scenario arguments supplied after the scenario name. The same arguments are supplied to `prepare`. Later phases must rely on persisted instance state rather than on caller memory of those arguments.

`cleanup` must be safe to invoke after a successful preparation, after a failed preparation, or for recovery from an interrupted preparation. Repeated `testlab close` of an already closed instance is successful without running cleanup again.

The baseline does not use Expect, `script(1)` or another PTY dialogue/handoff adapter. `enter` delegates directly to the scenario executable with the caller's standard streams.

## 4. Scenario environment

During all phases `testlab` exports:

```text
TESTLAB_PROJECT_ROOT
TESTLAB_SCENARIO_NAME
```

For `prepare`, `enter` and `cleanup` it also exports:

```text
TESTLAB_INSTANCE_ID
TESTLAB_INSTANCE_DIR
TESTLAB_CONTEXT_DIR
TESTLAB_RESOURCES_DIR
```

The paths identify the persistent instance record owned by `testlab`.

The scenario may write factual activity handles as regular files below `TESTLAB_CONTEXT_DIR`, for example a pathname, host, port, service endpoint or scenario-created credential. Context is data; it does not define assertions or commands.

The scenario uses `TESTLAB_RESOURCES_DIR` as its persistent ownership/recovery inventory. The first baseline deliberately does not impose a generic resource-record schema: ownership mechanics remain scenario-specific until multiple real scenarios demonstrate a common abstraction.

## 5. Persistent instance state

Persistent instance data is user-scoped technical state resolved through:

```text
state-path user sys testlab data
```

and organized by `testlab` below:

```text
<testlab-data>/instances/<instance-id>/
```

An instance id is an opaque controlled identifier generated by `testlab`. Callers must not derive semantics from its textual format.

Before `prepare`, `testlab` creates the instance record and stores at least:

```text
scenario
scenario-name
project-root
state
context/
resources/
```

`scenario` is a frozen executable copy of the selected scenario. The frozen copy is the lifecycle implementation for that instance. Subsequent `enter` and `close` therefore do not change behavior merely because the project scenario source is edited or removed after preparation.

The lifecycle states are:

```text
preparing
ready
failed
closed
```

If `prepare` fails, the instance remains persistent in `failed` state so its recorded resources can be diagnosed and cleaned. An interrupted invocation may leave `preparing`; `close` is permitted for recovery of both `preparing` and `failed`.

A successful close marks the record `closed`. The baseline retains closed records for diagnosis and defines no automatic retention/purge policy.

## 6. Public command interface

The first public forms are:

```text
testlab
testlab scenarios
testlab prepare <scenario> [<scenario-arg> ...]
testlab status [<instance-id>]
testlab context <instance-id> [<key>]
testlab enter <instance-id>
testlab close <instance-id>
```

`testlab scenarios` prints discoverable scenario names in ascending bytewise lexical order.

`testlab prepare` runs `check` before allocating an instance. On successful preparation it prints the new instance id and leaves the instance `ready`.

`testlab status` without an id lists persisted instances. With an id it prints the instance id, scenario name, lifecycle state and recorded project root.

`testlab context <instance-id>` lists context keys in ascending bytewise lexical order. With a key it writes that context file verbatim.

`testlab enter` requires a `ready` instance and invokes the frozen scenario `enter` phase.

`testlab close` accepts `ready`, `failed` and `preparing` instances, invokes the frozen `cleanup` phase, and marks the instance `closed` only after cleanup succeeds.

Bare `testlab` is the interactive-first surface. It uses the existing `menu` facility to present project scenarios and non-closed persisted instances. Enter prepares/enters a selected scenario or re-enters a selected ready instance; the close action closes a selected instance. Escape exits.

## 7. Failure classes

The public exit-status classes are:

```text
0  success
1  invalid invocation
2  scenario/instance/context not found or requested lifecycle state is incompatible
3  scenario lifecycle phase failed
4  testlab infrastructure or persistent-state failure
```

Signal-derived statuses from an interactive scenario are propagated when practical.

A lifecycle failure is not a test FAIL. It reports only that the requested scenario phase did not complete successfully.

## 8. Ownership and cleanup

Resource ownership is per resource, not inferred from the scenario substrate.

A scenario may mix:

```text
testlab-owned resources
externally owned resources
```

`cleanup` may destroy only resources whose ownership record says that the scenario owns them. Merely binding to an existing host, pathname, container, pod, service or other external resource never authorizes its destruction.

Persistent inventory is the recovery authority after interruption; shell traps alone are not sufficient lifecycle state for a long-lived scenario.

## 9. Interaction with testing and validation

Ordinary testlab use may target a dirty or uncommitted development checkout and need not produce PASS/FAIL evidence.

Permanent assertions remain normal `.test` files under `rumiai-tests`. `rumiai-test` remains semantically agnostic and does not acquire scenario-preparation responsibilities from this contract.

A future formal-validation integration may reuse a mature scenario environment only through an explicit testing/validation contract. Ordinary testlab state is not formal validation evidence.
